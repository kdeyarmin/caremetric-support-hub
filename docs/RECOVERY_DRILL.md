# Hub data recovery

CI runs a destructive logical-data drill only inside its disposable Supabase database. `server/recovery-integration.mjs` requires GitHub Actions, an explicit opt-in, the exact local test connection and a matching local Supabase database container. It cannot accept a production connection string.

The drill creates a synthetic customer case, public reply and private note through the actual SMS-authorized repository. It exports every `hub` and `private` table and sequence using PostgreSQL's custom archive format, truncates that exact domain without cascading to other schemas, and restores the archive in one transaction. It compares every row and sequence, validates unchanged grants/RLS/function definitions/trigger modes, reads both customer and staff case views, and replays the original request keys to prove no duplicate messages or cases. It finally revokes restored SMS sessions and pending challenges and verifies that old sessions cannot read the restored case. Dumps stay inside the disposable container and are never uploaded as CI artifacts.

This is application-data recovery into the same migrated schema. It does not establish production backup retention, full project disaster recovery, provider Auth recovery, custom-role credential recovery or Storage object recovery. Supabase database backups contain Storage metadata, not object bytes; its daily backups also omit custom-role passwords. See [Supabase backup documentation](https://supabase.com/docs/guides/platform/backups) and [PostgreSQL archive documentation](https://www.postgresql.org/docs/current/app-pgdump.html).

For a production recovery, keep traffic and native command dispatch closed while restoring into a separately verified target. Match the exact schema release and migration history, restore Auth identities and relationships from the same recovery point, and restore private object bytes against their recorded SHA-256 values. Recover the restricted server-role credential through the secret store. Revoke restored sessions/challenges and invalidate outstanding one-use capabilities before reopening traffic. Reconcile every in-flight native command and provider operation against its original command ID and provider idempotency key; an old database snapshot must never trigger an automatic replacement payment, publication or access change. Verify current native permissions, customer isolation, public/private media behavior, immutable receipts and audited case history before switching the Hub origin.

Production completion evidence must include the actual available backup range, the chosen recovery point, a successful separate-target restore, object-byte verification, measured recovery time and a traffic rollback record. The CI drill alone is not that evidence.
