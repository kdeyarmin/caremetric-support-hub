# DocStudio publication imports

This change adds the reviewed executor for the existing `caremetric.support-hub.publication.v1` contract. It imports knowledge articles and videos into the existing Hub catalog. Course completion, enrollment, native billing, and canonical learner identity writers are untouched. Source code and passing tests do not establish that this feature is deployed; release requires the migration and protected Storage transport below.

DocStudio authoring and rendering are retired. The shared importer and
`publication-media` transport remain available for approved packages using the
existing `source_system: "docstudio"` manifest contract and source-version rules.
They do not require the retired DocStudio tables, worker or `docstudio-media`
function; `hub-publications` is separate from the retired `hub-docstudio` bucket.

## Editor workflow

1. Obtain an approved manifest package and its original assets in the existing DocStudio publication format. Open **Review material imports** (`/imports/docstudio`) in the Hub using the current SMS session.
2. Select the manifest (at most 64 KiB) and its exact files. Articles require one Markdown file (2 MiB maximum). Videos require MP4, WebVTT captions, and a plain-text transcript; all three hashes must differ. Both sidecars are required and have a 10 MiB limit. Video duration is at most 24 hours.
3. Approve the source version and human PHI-free review. The Hub verifies every byte count/hash and the existing text, MP4 header, and timed caption rules, then shows the current catalog changes.
4. Explicitly confirm each placement replacement, retirement, and reactivation, then commit the exact reviewed plan. A lost response can be retried with the same request key. Changed request keys or stale previews require a new review.

Names are display-only. The part names are `primary`, `captions`, and `transcript`; filenames never select a storage object. There is no archive parser, URL fetch, remote session handoff, or automatic publication when files are selected. Text is rendered using the existing escaped article renderer. Human review remains necessary: text checks cannot certify arbitrary prose or inspect video pixels for PHI.

The initial application video limit is **25 MiB** and is read from `private.publication_import_settings`. This is a conservative configured application limit, **not a verified Supabase project maximum**. The project setting could be lower, in which case Storage rejects the transfer and no catalog commit occurs. Raising the setting (up to the protocol ceiling of 512 MiB) requires verifying project/runtime capacity. Exporter limits do not change this application limit.

## Boundaries and persistence

- Same-origin `/api/publications/` editing endpoints use the existing app-owned HttpOnly SMS session. Stage, upload, preview, commit, receipt replay, and private media recheck the current session and relational authority. Public media uses the separate download-only policy below. No uploaded manifest field supplies a role or product permission.
- Desired products must be registered and enabled. An editor needs current `content.write` (or `platform.admin`) on every desired and existing affected product, including removed placements. Existing non-import catalog keys are rejected rather than merged. A stable key cannot change kind or locale.
- Intents expire after 30 minutes. There are at most 3 open intents per editor, 12 globally, 100 starts per hour, and 2 concurrent local upload spools per Node instance. Each upload streams into a random private temp directory, hashes with backpressure, validates bounded text or a 64 KiB MP4 header, then streams the exact bytes to Storage. Temporary local bytes are deleted on success and failure.
- The private `hub-publications` bucket has no browser read/write policy. A separate closed `publication` audience uses the existing 30-second single-use capability machinery. The Edge transport rechecks the live Hub authority, hashes the streamed bytes again, uses a fixed bucket/path, and rejects upserts. Only a verified upload response permits the server to record verification.
- If Storage accepted an immutable upload but its response or subsequent SQL verification was lost, retry the same file while the intent is open. Node checks the local bytes again. On an exact Storage 409, or a bounded recognized legacy duplicate response, Edge streams and hashes the existing object at that same fixed key with the original transfer deadline, length cap and MIME check. Only exact matching bytes can reconcile the lost verification; it never overwrites or deletes an object. Unrelated 4xx errors cannot trigger reconciliation. See the [Storage error codes](https://supabase.com/docs/guides/storage/debugging/error-codes) and [native duplicate codes](https://github.com/supabase/storage/blob/master/src/internal/errors/codes.ts).
- The transactional commit locks the content key and request key. It compares both the pure preview snapshot and an authoritative catalog fingerprint, checks every confirmation, inserts an immutable revision/provenance record when necessary, attaches verified assets, expires removed placements, and upserts the existing unique item/product placement rows. The audit contains IDs, outcome, revision, and plan hash only, never article bodies, manifest payloads, or filenames.
- Replayed identical commits return the same receipt after current authorization. A reused key with another payload or intent fails. Imported revisions and source provenance cannot be changed or removed. Published assets cannot be reassigned or deleted through staging cleanup.
- A higher `docstudio-vN` becomes the approved next version only inside the authorized Hub review workflow. Version gaps are allowed when explicitly approved; rollback and changed content under the same version remain rejected. An already retired source version cannot be reactivated without a higher version.

## Media and cleanup

Published video and sidecars use `/api/publications/media/<revision UUID>/<part>`. The browser receives no Storage path, service credential, signed URL, or provider locator. Customer/staff metadata, GET, HEAD, and ranges require a current SMS session and actual per-revision publication policy. Public Help media is available anonymously only when that same policy permits the current public approved publication, active product and unrestricted audience. Public metadata and HEAD re-evaluate this policy directly; GET creates a separate 30-second, single-use, actor-free download ticket, checked again at the fixed `/api/internal/publications/public/authorize` endpoint before Edge reads bytes. The evaluator explicitly clears staff claims; this ticket can never upload, read staging, or grant customer/staff access. At most 2,000 unconsumed public tickets may exist and expired tickets are deleted on issue. Suffix/open-ended ranges normalize to a single bounded range; multiple or malformed ranges fail. Retirement, audience restriction or permission revocation blocks the next request.

Cleanup runs on server startup and every 15 minutes, at most 20 intents per run. A separate one-use maintenance ticket can name only an intent expired for at least five minutes whose objects are not attached to a revision. The grace exceeds the fixed 120-second Node and 110-second Edge transfer deadlines, so a pre-expiry upload cannot finish after its key is cleaned. The Edge function consumes that ticket and deletes at most the three fixed object keys. Published objects and durable commit receipts remain preserved. Failed or incomplete transfers stay private and are retried by cleanup after expiry; they never become readable catalog content.

## Reviewed deployment requirements

1. Apply `20260911174023_docstudio_publication_imports.sql` only after SQL and combined-contract review. It adds private importer records, the private bucket, guarded server-only functions, and the additive delegation audience. It preserves `carebase.learning` and existing media audiences.
2. Deploy `publication-media` with the Supabase gateway JWT check disabled **only because it receives opaque single-use Hub capabilities**. Its own fixed Hub introspection remains mandatory. Keep `SUPABASE_SERVICE_ROLE_KEY` in the Edge runtime only. Do not change existing `app-media` configuration.
3. Deploy the Node/frontend image, including the shared import protocol and preview modules in the production image. Confirm the private bucket and conservative configured upload limit. Do not advertise a larger verified Storage capacity without checking the project setting.
4. Run negative hosted checks for missing/forged/reused capability, Origin/Cookie, revoked session, inaccessible revision, and arbitrary paths. Run an owner-approved synthetic import before enabling real content. Root release coordination owns production changes and any feature declaration under API contract 4.

Validation includes unchanged pure-planner tests, strict request/response tests, streamed hash/range tests, actual React confirmation/retry tests, the actual Edge handler with synthetic HTTP fixtures, pgTAP privilege/immutability contracts, and a disposable PostgreSQL + real SMS HTTP + Edge composition. Only external Storage bytes are synthetic in the composition. No production data or financial writes are required.
