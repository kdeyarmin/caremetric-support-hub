# Governed course package ingestion

The preserved CareBase draft workspace offers original SCORM/xAPI ZIP retention and a separate reviewed runtime acceptance. The Hub never executes archive content in the administrator session. LTI packages remain informational. This does not publish a course or create learner completion evidence.

The browser uses the existing SMS HttpOnly session at `POST /api/admin/packages`. JSON operations are closed context, status, accept and finish requests. Upload is raw `application/zip` with canonical UTF-8 base64url JSON in `x-caremetric-package-request`. Browser metadata includes the course/version scope; the server strips that wrapper before forwarding to the fixed `https://cmcarebase.com/api/learning-admin/package` endpoint. Caller URLs, object paths, native credentials and arbitrary operations are unsupported.

The Hub hashes and forwards ZIP chunks with backpressure, enforces the exact declared byte length and SHA-256, limits compressed input to 50 MiB, and aborts stalled input after 120 seconds or client cancellation. Native CareBase separately validates the archive, limits expanded content to 100 MiB, preserves immutable private original bytes, and derives the runtime artifact. Replies are bounded to 262,144 bytes; context contains at most 20 intents. These limits are enforced independently of the file-picker hint.

Staging and finishing each use a fresh, single-use `carebase.learning` delegation bound to the exact closed native operation and original current SMS session. The native current global administrator mapping and source compare-and-swap remain authoritative. The Hub also requires its preserved source head before and after staging, and the exact operation/request pair plus preserved pre-write source before finishing. It checks current session authority again after native work. Upload or acceptance staging does not automatically finish.

CareBase owns the durable intent ledger. Reloading retrieves current-actor context, including whether the original session can still finish each staged operation. Request IDs can repeat across sessions; operation IDs are the global identity. A reviewed request keeps the same request ID on an uncertain retry. Context/status remain observable with stale source, but cannot grant a finish for another session or adopt later edits. An immutable result contains its original post-commit SHA; the intent retains its original pre-write SHA. Successful changes require the administrator to load and preserve the new exact source before another edit. The Hub does not silently advance that head.

Availability comes from all five native `learning.packages.*` capabilities (context/status/upload/accept/finish). Native rollout requires its reviewed ingestion SQL, private storage and explicit feature flag; Hub deployment alone does not establish readiness. No additional Hub migration, feature gate or browser key is required. Existing course review, package runtime access policy and learner completion writer remain the shared native implementations.

Validation includes closed/adversarial protocol and client tests, explicit-confirmation/reload/uncertain-response UI tests, a stalled real HTTP upload cancellation test, and `server/package-integration.mjs` against disposable Hub PostgreSQL and actual SMS/HTTP delegation flows. The latter uses deterministic native responses; CareBase CI independently validates native SQL, Storage and real ZIP processing. Cross-repository composition tests exercise the actual native handler and Hub projector together. No production packages are uploaded by these tests.
